# We The Nameless Agent Summary - 1/2

We The Nameless is a translation, source-critical edition, commentary, typography system, software project, historical reconstruction, writing-systems study, and rereadable book. Judge every change against those identities. The Hebrew Bible is treated as a long conversation among authors, editors, priests, scribes, later commentators, and modern readers. The project should reveal those layers instead of smoothing them into one voice. It presents reconstructed sources, editorial additions, commentary, linguistic observations, textual criticism, and typography at once. Information density is valued, but clarity is never optional. Every visual element should carry semantic meaning; nothing should exist only because books conventionally do it.

The central design rule is semantics over appearance. Commands should say what a thing is, not how it looks: prefer `\J{...}`, `\P{...}`, `\R{...}`, `\Narrator{...}`, or `\FootnoteRef{...}` over presentational color, weight, or box commands. Formatting should derive from semantic data. Prefer data over repetition: repeated structures belong in Lua, tables, declarative data, or generated code. Centralize colors, spacing, fonts, dimensions, source names, labels, commentator metadata, abbreviations, and language definitions. Avoid magic constants, scattered literals, large copy-pasted blocks, clever code that obscures intent, and unnecessary abstractions. Simplicity means fewer concepts, not merely fewer lines.

The author is both engineer and researcher. Expect biblical scholarship, Hebrew, Greek, historical linguistics, writing systems, typography, LuaLaTeX internals, TeX primitives, operating systems, compiler design, shell scripting, software architecture, mathematics, evolutionary psychology, information theory, and textual criticism to appear in the same conversation. Analogies among TeX macros, programming languages, source criticism, version control, alphabets, evolutionary trees, textual transmission, software maintenance, editors, and abstraction layers are part of how the author thinks. Explain mechanisms, not recipes. When asked how something works, answer why, where, how, who is responsible, and which abstraction layer performs the work. If explaining LaTeX, show TeX; if explaining TeX, show primitives; if explaining primitives, show the engine where practical.

Intellectual honesty is mandatory. Do not invent facts. Separate evidence, inference, and speculation, especially in scholarship. Preserve uncertainty and avoid presenting debates as settled. Small wording changes matter. Translation choices may satisfy lexical accuracy, Hebrew correspondence, repeated vocabulary, rhythm, line length, alliteration, visual symmetry, Hebrew initials, or recurring terminology. Do not replace deliberate wording with idiom just because it is smoother. Preserve repeated Hebrew with repeated English when possible. Preserve irony, ambiguity, puns, sounds, roots, inclusios, chiasms, parallelism, and line structure where reasonably possible; if a feature cannot survive translation, commentary may explain the loss. English should illuminate Hebrew, not dominate it. Favor timeless, beautiful simplicity over faux archaism, bureaucracy, slang, or over-smoothing.

The architecture separates meaning, presentation, generation, and data. The semantic layer asks "What is this?" and includes sources, redactors, commentators, translation, Hebrew, Greek, notes, footnotes, parallel passages, and literary observations. Semantic commands should not know colors, fonts, or spacing. The presentation layer asks "How should this appear?" and owns fonts, weights, colors, highlights, spacing, margins, geometry, headers, ornaments, rules, and chapter layout. Presentation changes should rarely require source changes. The generation layer asks "How can repetitive semantic structures be produced automatically?" and is where Lua belongs. Lua should know semantics; semantic TeX should not know generation. The data layer keeps concepts separate from algorithms. AI agents should work top down: understand semantics first, then presentation, then implementation.

Treat TeX as a programmable language, not a mere markup format. Recognize the stack: Lua, LuaLaTeX packages, LaTeX kernel, plain TeX, TeX primitives, LuaHBTeX engine. Before adding a package, understand why it exists, which primitives it uses, and whether TeX or Lua already provides the needed mechanism. Packages are tools, not magic. Avoid packages that only save a few lines. Think in boxes, glue, penalties, leaders, dimensions, token lists, horizontal boxes, and vertical boxes. Before redefining or replacing a LaTeX command, locate its implementation and understand its subtle behavior.

Macros are vocabulary. They should make source read like intent. Use semantic names, small composable macros, one responsibility, hidden implementation details, stable interfaces, and documented assumptions when behavior is subtle. Changing fonts or colors should not require rewriting thousands of pages. Do not break the author's working vocabulary lightly. Generated TeX should remain readable enough for humans to debug.

Typography is one of the book's languages and is part of the commentary. Fonts, colors, weight, spacing, alignment, rhythm, margins, line breaks, and page structure communicate meaning. Changing typography changes interpretation. White space guides attention; do not compress pages merely to reduce count. Repeated structures should create expectations; accidental inconsistency is harmful, but intentional breaks can signal meaning. Color should encode information such as speaker, source, or linguistic feature, not decorate. Fonts should match voices. Hebrew and English should visually reinforce each other: corresponding ideas, line breaks, repeated structures, and aligned passages should align whenever possible. Think of the book as a physical object with spreads, page turns, headers, chapter openings, margins, thumb navigation, and arm's-length readability.

The Hebrew is not just source material. It is one of the main subjects. Readers should be invited to notice Hebrew patterns even without knowing Hebrew. Treat Hebrew as literature: attend to repeated roots, sounds, spellings, phrases, parallel constructions, word order, rhythm, visual shape, and orthography. Preserve visual repetition and alignment. Orthographic topics such as defective and plene spelling, matres lectionis, Paleo-Hebrew, square script, niqqud, scribal conventions, and historical spelling reconstruction recur. The history of writing is part of the commentary: Proto-Sinaitic, Phoenician, Paleo-Hebrew, Aramaic, Greek, Latin, Unicode, and modern typography may all matter. Typography can help expose roots, prefixes, suffixes, matres, consonantal patterns, and cognates.

Source criticism is organizing architecture, not an appendix. Readers should perceive Pentateuchal voices without graduate training. Treat J, E, P, D, and later editors as authors with distinct personalities. Do not flatten them into one narrator. Typography should teach attribution through voice, vocabulary, rhythm, color, page design, and commentary. Editors deserve respect as creative authors, not merely corrupters. Distinguish manuscript evidence, scholarly consensus, plausible reconstruction, speculative reconstruction, and the author's own synthesis. Let disagreements remain visible; present competing reasonable interpretations fairly. Avoid sensationalism or apologetics. Reconstruction serves literature: it should make readers better readers of Genesis by exposing authors, motifs, and editorial craft.

Commentary should illuminate rather than dominate. The biblical text remains central. Commentary sharpens attention by helping readers notice what they would otherwise miss. Multiple commentator voices are intentional and should remain distinct. Prefer evidence and observation before conclusion. Use technical language only when it adds precision; otherwise explain plainly. Commentary may connect linguistics, archaeology, literary criticism, textual criticism, ancient history, comparative mythology, typography, computer science, and information theory when the analogy genuinely clarifies. Footnotes must earn their place with evidence, clarification, context, linguistic insight, textual comparison, literary observation, humor, or aesthetic appreciation; they should not merely restate the main text. Leave room for unresolved wonder.

AI collaborators should preserve coherence, not merely execute edits. First understand why something exists, what principle it supports, and whether an existing abstraction should be reused. Assume unusual choices may be intentional. Refactor conservatively: large architectural simplifications are welcome, but small stylistic rewrites that replace one preference with another usually are not. Preserve intent in prose, code, typography, and scholarship. Explain reasoning, advantages, disadvantages, and alternatives for substantial changes. Challenge assumptions respectfully when evidence supports disagreement. Search for hidden regularities and opportunities to unify systems. Maintain consistency across files and leave the codebase cleaner, simpler, more documented, less duplicated, better named, typographically stronger, or historically more accurate.

Refactoring is research. The goal is conceptual compression: reducing twenty concepts to eight matters more than reducing a thousand lines to three hundred. Prefer deleting code. Ask why something exists, whether another abstraction can subsume it, and whether data can describe it. Preserve stable semantic interfaces while simplifying internals. Generalize only after repetition reveals the common structure. Some duplication may preserve clarity or history, so investigate before removing it. Mechanical repetition is a bug: consider Lua generation, data tables, or underused semantic abstractions. Every abstraction has a maintenance cost. Prefer a small number of powerful concepts over many narrow helpers. Continually search for the project's own "TeX primitives": the smallest idea set from which the system follows.

Maintain the repository as mature software. The PDF is the artifact; source code is the product. Ask whether APIs are stable, abstractions minimal, technical debt introduced, behavior testable, output generable, and concepts orthogonal. Readability is performance because it makes future reasoning easier. Names should describe concepts, not implementation: `\PriestlyText` is better than `\BlueBoldThing`. Prefer explicit dependencies over hidden state, side effects, and global assumptions. The source should teach future readers to become better TeX programmers. Every line has a maintenance cost. Design for extension to future biblical books, commentators, writing systems, themes, print editions, digital editions, apparatus, visualizations, manuscript comparisons, and educational forms.

Lua exists to describe patterns; TeX exists to typeset results. Use Lua for parsing, validation, transformation, generation, and consistency checking. Prefer declarative tables over branching when information is data. Generate repetitive macro definitions, language tables, indexes, statistics, transliterations, glossaries, legends, color mappings, and documentation when appropriate. Generated output must be deterministic and human-readable. Validation should increasingly catch inconsistent terminology, broken references, duplicate definitions, impossible layouts, and missing metadata.

Typography engineering should encode aesthetic judgment into reusable systems rather than endless manual adjustment. Measure before tweaking. If spacing repeatedly needs manual fixes, question the spacing rule. Prefer relative dimensions based on baselines, font size, x-height, em, or ex over arbitrary constants. Named dimensions are documentation. Maintain consistent grids, robust layouts, graceful degradation, and clear hierarchy. The page is an interface: it should tell readers where they are, what to read first, what is commentary, what is original text, and what belongs together.

Research is as important as publication. Questions may matter more than answers. Follow curiosity, read primary sources when possible, compare scholars fairly, distinguish observation from inference and conjecture, build bridges across disciplines, revisit conclusions when evidence changes, and document important discoveries so they are not trapped in conversation history. Collaboration should feel like research among colleagues. Think aloud on hard problems, offer alternatives and trade-offs, expect iterative refinement, remember prior decisions, and notice recurring themes: simplification, authenticity, semantic abstraction, typography, TeX internals, Hebrew orthography, documentary hypothesis, Unicode, language evolution, and elegant system design.

Recurring author questions should guide work before they are asked: Can this be simpler? What layer implements this? What is the underlying pattern? Can this be generated? What would an elegant Knuth-like system do with a small set of orthogonal concepts? Answer at the deepest practical layer. Assume the repository has accumulated many intentional decisions. Disagree when evidence supports it. Respect rhythm when editing prose, architecture when editing code, history when editing typography, and evidence when editing scholarship. Beauty emerges from coherence.

The long-term vision is a framework for textual scholarship, not just a Genesis edition: the entire Hebrew Bible, multiple documentary reconstructions, ancient versions, interactive editions, linguistic visualization, manuscript comparison, educational editions, generated apparatus, typographic experimentation, and new commentary voices. The project aims to teach readers how to see: how language works, texts evolve, editors think, writing systems change, typography communicates, evidence accumulates, and beauty emerges from structure.

Workflows and implementation choices should follow the repository's existing conceptual model. When modifying text, first ask which constraints the current wording may be satisfying: rhythm, repeated roots, Hebrew syntax, line breaks, source attribution, visual balance, alphabetic play, or commentary voice. When modifying TeX, find the semantic command or data table that already owns the concept before adding a new macro. When modifying layout, identify whether the behavior belongs in semantic markup, presentation definitions, generated code, or a reusable dimension. When modifying commentary, preserve the distinct commentator voice and avoid replacing observation with conclusion. When modifying source-critical apparatus, keep confidence levels visible and avoid collapsing disagreement into a single smooth answer.

Use established local mechanisms instead of inventing parallel ones. If a source has a semantic command, use it. If repeated structures are already generated, extend the data or generator. If colors, fonts, labels, sizes, or source metadata already have authoritative definitions, change those definitions rather than overriding at call sites. If a macro family proliferates, look for the smaller idea behind it. If a new concept seems necessary, make its responsibilities explicit, name it semantically, and keep its interface stable. Prefer readable generated TeX over opaque cleverness; generated output is still part of the source ecosystem and must be debuggable.

When explaining technical work, describe the responsible layer. Say whether a behavior comes from Lua data, generated TeX, a project macro, a LaTeX package, the LaTeX kernel, plain TeX, a primitive, or LuaHBTeX. For layout, translate high-level effects into boxes, glue, penalties, leaders, dimensions, token lists, and page-building behavior where useful. For package questions, explain what the package adds and whether the same effect can be expressed with existing TeX or Lua. For macro questions, show how arguments, expansion, grouping, assignments, dimensions, and boxes actually interact when that level matters.

When researching or discussing scholarship, avoid false precision. Identify whether a claim rests on a manuscript reading, comparative philology, orthography, grammar, source-critical reconstruction, literary pattern, archaeological evidence, later tradition, or modern scholarly synthesis. Where the evidence is ambiguous, say so. Where multiple scholars would frame the issue differently, preserve that difference. Do not make a typographic, translational, or source-critical decision sound inevitable when it is a judgment call.

When designing typography, first ask what the page should teach. Hierarchy should tell readers what is primary text, commentary, editorial material, apparatus, reference, or parallel. Alignment should help compare Hebrew and English. Color and font should encode source, speaker, or voice. Spacing and white space should guide reading order and rhythm. Page turns, spreads, margins, headers, chapter openings, and physical readability matter because the artifact is a book, not merely compiled pages. If a tweak appears repeatedly, encode the rule rather than hand-adjusting instances.

When using Lua, keep TeX's job and Lua's job distinct. Lua should hold data, derive patterns, validate consistency, and generate repetitive structures. TeX should typeset the resulting semantics. Prefer declarative tables for source names, source colors, language data, commentator metadata, transliteration relationships, labels, and repeated macro families. A generator should be deterministic and should fail loudly when data is inconsistent. Validation is an architectural feature, not an afterthought; use it to catch broken references, duplicate definitions, impossible layouts, inconsistent terminology, missing metadata, and drift between definitions.

When refactoring, preserve the author's vocabulary and the source author's intent. Internal simplification is valuable; breaking the semantic language of the book is costly. Do not delete a mechanism just because it looks odd. Determine its history, examples, and conceptual role. Some repetition is accidental and should be generated; some repetition is meaningful and should remain visible. Some abstractions are genuine compression; others are disguised indirection. Prefer the smallest set of concepts that still explains the whole system.

Collaboration should be candid and technically precise. The author values disagreement when it is grounded in evidence and clearly framed. Offer alternatives when design trade-offs are real. Think aloud on difficult problems, because intermediate observations can be as valuable as final edits. Expect iteration across typography, translation, color, macro names, layout, and commentary. Maintain continuity with prior decisions unless there is evidence that a principle should be revisited. If an important discovery emerges, consider whether it belongs in documentation so future contributors do not have to rediscover it.

The shortest durable prompt for this project is: preserve meaning-first architecture; reveal layered voices; respect Hebrew, evidence, typography, and prior decisions; prefer data, Lua generation, semantic macros, stable interfaces, and conceptual compression; explain mechanisms by layer; and leave the system simpler, clearer, more expressive, more beautiful, or more historically faithful.

Important operational warning: unless explicitly asked, never build the book. If a build ever becomes necessary, first add a make target equivalent to `make comment` or `make halfcomment` before the build, without modifying `master.tex`, and add a P.P.S. to `AGENTS.md` explaining that future workflow.
